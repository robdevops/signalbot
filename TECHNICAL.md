# Technical notes

For what happens to your messages and data, see [PRIVACY.md](PRIVACY.md). For how the code is laid out and how to add a feature, see [CONTRIBUTING.md](CONTRIBUTING.md).

Go, the standard library plus `golang.org/x/image` (for chart text, with the bundled Go fonts); one static binary. The bot is a small core and a set of features. The core answers messages on its own; each feature is a package that registers on the core's ports (`internal/feature`) and can be deleted without changing the core. `cmd/signalbot/features.go` lists them, one line each.

## The core

- **Receive.** JSON-RPC to `signal-cli daemon` over a unix socket or TCP (`listAccounts` once per connection to learn its own ID). If the connection drops it reconnects, waiting 1s, doubling up to 32s, reset once a connection has held for a minute; requests in flight fail rather than hang. Frames are capped at 1 MiB. The bot's own messages are ignored.
- **Addressed or not.** A message is answered if it mentions the bot, replies to one of its messages, or is a DM from a sender in `SIGNAL_DM_USER_IDS`. A DM from anyone else is dropped and only the sender's ID is logged. An unaddressed group message goes to the features' `OnMessage` hooks on the reader goroutine and is never logged.
- **Names** come from signal-cli's contact list (`listContacts` with `allRecipients`, at most 5,000), loaded on connect, on every group `UPDATE` event, and when a mention is unknown or the list is over 24 hours old, at most every 15s, with requests meanwhile folded into one. A group `UPDATE` also clears the names that chat remembers for turning `@Name` into mentions. An unresolved mention reaches the model as `[unnamed user]`; a group sender with no known name gets no prefix; an unknown quote author is "someone". The bot calls itself by its profile name, or `signalbot`. A name two people claim is never linked.
- **Concurrency.** The reader goroutine decides "addressed?" without calling the network. Everything that may (waiting for the account ID, reloading contacts, sticker labels, media, the model) runs in a worker slot, of which there are `MAX_CONCURRENCY`. Each chat has a mailbox of at most 4 waiting messages and at most one worker, which answers them in order, so each answer sees the ones before it; different chats run in parallel. A full pool or mailbox drops the message with a warning.
- **Answer.** Typing is shown until the reply is ready. The prompt is built (below) and sent to OpenRouter. On failure the "OpenRouter error" line is logged, the chat gets "Sorry, I couldn't get an answer right now.", and history is unchanged. The reply has the bot's own @name stripped, @Name linked to real mentions, is split at 2,000 characters and capped at 4 messages.
- **The model.** OpenRouter's chat completions API over a keep-alive client that requires TLS 1.3 and keeps up to `MAX_CONCURRENCY` idle connections. Requests set `provider.data_collection: deny` and the `MODEL_REASONING` effort, and ask for the real cost, which is logged. A network error, 429 or 5xx gets one retry; an error body is reduced to its message. The tool loop takes at most 5 requests and 3 minutes per reply, and 4 pictures. At startup the model list says whether the model takes images and can call tools; tools are offered only if it can (otherwise one warning says "tools are off"). If the check fails or the model isn't listed, images are off and tools stay on.
- **History.** Per chat, `HISTORY_TURNS` exchanges, in memory only, for at most 500 chats. Each entry expires after 24 hours, or sooner when the chat's disappearing-messages timer (`expiresInSeconds`) runs out, on one `time.AfterFunc` per chat set for its earliest entry. When a chat's history is gone, its remembered names and tool follow-up counts go too.
- **Timers.** One-shot timers for features (`At`), kept in a min-heap on one goroutine that sleeps until the next is due, but at most a minute, comparing wall-clock times, so a suspend or clock jump is noticed within a minute. A callback always runs, however late, and is passed the time it was due; it takes no slot. At most 10,000 timers. They live in memory and start once the bot first connects. The time zone is the local one (`TZ`; the image ships tzdata).
- **Safe under load.** Concurrency, mailboxes, history, chats, names and frames are capped. The same message from the same sender in the same chat within 10 seconds is dropped. Display names and quotes are sanitised before they reach the model or the log.
- **Logging.** journald priorities 2–7, all always written: `<2>` errors that stop the bot, `<3>` errors, `<4>` warnings, `<5>` startup, connect and reconnect, `<6>` info, `<7>` debug. Under journald (`JOURNAL_STREAM` matches stdout) each line carries its `<N>` prefix; elsewhere, as in Docker, lines are plain, with a timestamp only in a terminal. Priorities 5–7 go to stdout and 2–4 to stderr. Each addressed message logs "received group chat" or "received dm" at info, with no name or content. Message text is never logged: a panic while handling a message is recovered and reported without its value or stack; API error bodies are reduced to their message; malformed frames are reported by size. Every logged value has `\n` and `\r` escaped, so no value can start a forged line.
- **Shutdown.** On SIGTERM or SIGINT, timers and new work stop, work in flight drains for up to 8s, then the socket closes and the bot waits for what features run with `Go`.
- **Configuration** is environment variables only; `-version` prints the version. Runs under systemd or Docker (hardened unit and image included; the image is pinned by digest and has no shell). `MemorySwapMax=0` in the unit and `--memory-swap` equal to `--memory` in Docker keep history out of swap.

## The prompt

Each request sends a system prompt, then the chat's history, then the new message.

The system prompt is, in order:

1. The built-in prompt:

   > You are a helpful assistant in a Signal chat. Reply in plain text: Signal does not render markdown. Aim for a single line. Two or three sentences at the very most, and only when asked for detail. Never exceed 2000 characters, which is Signal's limit for one message. A mention shown as [unnamed user] is someone whose name you don't know; don't invent one. To mention someone, write @ followed by their exact name. Never write your own name with an @.

2. When the model can call tools and any are registered, the tools line: `Your tools: ` and the listing of each tool group offered for this message, then `If asked what tools you have:` and the names of every group, offered or not. For example: `Your tools: web search; charts (make_chart, make_pie_chart); weather: get_forecast, /forecast. If asked what tools you have: web search, charts, get_forecast, /forecast.`
3. The `System` line of each offered tool group (an MCP server's `prompt`), then the lines features add for this message.
4. `MODEL_SYSTEM_PROMPT`, if set. It adds to the built-in prompt and never replaces it.
5. The introduction rule, always last: `If asked to introduce yourself, reply with exactly this text and nothing else: "…"`. The quoted text is `INTRO` with `{name}` (the bot's profile name, else `signalbot`), `{model}` (without the `provider/` prefix) and `{tools}` (every group's names in feature order, or `none` when there are none or the model can't call tools) filled in. It is quoted so a newline or quote in it can't escape into the rest of the prompt.

The history is at most `HISTORY_TURNS` exchanges, none older than 24 hours. In a group each message is prefixed with its sender's name ("Alice: …"). A quote is added as `[Replying to a message attributed to you: "…"]` when it is the bot's own, or `[Replying to a message by "Bob": "…"]` otherwise. Quotes are escaped and capped at 500 characters, because the sender composes them. A picture sent with a reply is kept in history as its note (for example `[sent the chart "NVDA"]`), or `[sent an image]`.

A tool group without keywords is offered with every message. One with keywords is offered when the message matches, and for the 2 replies after any reply that matched or used one of its tools. A chat command offers only its tool, and requires the model to call it (`tool_choice`) until its result is in.

## Features

In `features.go` order, which is the order hooks run in and of the tools line and `{tools}`.

- **`example`** answers `/example` itself, never through the model, with what the bot can do, its model and tools, and a real @mention of whoever asked in a group. It leaves no history.
- **`websearch`** offers OpenRouter's server-side web search tool (`openrouter:web_search`), which the model calls only when it decides to, unless `MODEL_SEARCH` is off. It logs "web search on" at startup.
- **`groupctx`** (`GROUP_CONTEXT`, on by default) keeps each unaddressed group message as context: `Name: text`, capped at 2,000 characters, with photos and stickers noted as `[image]`/`[sticker]` but never fetched. The core keeps it like any history entry and never logs it.
- **`vision`** adds a message's images (and a quoted message's thumbnails), up to 4 and 5 MB each, fetched with `getAttachment`, and its sticker, fetched with `getSticker` and labelled with its emoji and pack title from `listStickerPacks` (quoted, since anyone can make a pack). If the model takes images they go as image parts; otherwise the model is told it can't see them, and a sticker still gets its label. So a photo or sticker alone is answered in a DM or a reply to the bot. History keeps only a note, which tells the model it sees images only in the latest message, so to look again someone replies to it and mentions the bot.
- **`charts`** offers `make_chart` and `make_pie_chart` when a message asks for a chart (chart, graph, plot, visualise/visualize, pie, donut and their forms), and for the 2 replies after. `make_chart` draws line charts of up to 6 series on one or two Y axes, each with its own mode (values as given, or % change from each series' first point), unit, title and optional inversion; a single series is an area, green if it ends up and red if down, with its high, low and current value marked. `make_pie_chart` draws 2–12 shares of a total as a ring, largest first, with the percentages and the shortened total (K, M, B, T) computed by the bot. Charts are 1280×800 PNGs on white. A reply with a chart is the chart alone, captioned with its title (and subtitle, if both fit on one line) in place of the model's text; history notes it by caption.
- **`mcp`** (`MCP_CONFIG`) connects to MCP servers: remote ones over Streamable HTTP (JSON or server-sent events, with the session re-established if the server forgets it) and local ones over stdio (restarted with backoff if they exit, given only `PATH`, `HOME` and their `env`, and stopped when the bot stops). Each server is one tool group: `allowed_tools` or `blocked_tools` decide its tools, named `server__tool` for the model; `prompt` is its system-prompt line while offered; `keywords` gate it like the chart tools. A server's own `instructions` from the MCP handshake are not used, so a server can't add text to the prompt. Each call has 30s and its text result is capped at 16K characters; images in a result are sent with the reply, up to 4. Tool results are untrusted input to the model, like a quote. Only the question and the final answer go into history; arguments and results are never logged. `chat_commands` make `/name text` a turn in which only that tool is offered and must be called; with `require_arg`, a bare `/name` is answered by the bot. Names are checked at startup (letters, digits, `_`, `-`; not taken; the tool offered) and skipped with a warning otherwise; none is registered when the model can't call tools. A last group holds only every server's `/commands`, sorted, so `{tools}` lists them after every tool. It logs "MCP tools:" and "chat commands:" at startup.
- **`schedule`** is `/schedule`, with `/timer` and `/reminder` as aliases (see the [README](README.md#scheduling)), only in a DM from a sender in `SIGNAL_DM_USER_IDS`. Each schedule is a timer; at each run the text is delivered (`Deliver`) as if the user had just posted it in the DM or the group: plain text is posted by the bot as written, with @Name linked to the group's members; text that mentions the bot is answered; a `/command` runs. A group is matched by name among those the user shares with the bot (`listGroups`) and kept by ID, so a rename doesn't break it; a run in a group the user has left is dropped and logged. A repeating schedule skips missed runs and is always set from the clock; a one-shot up to an hour late runs, an older one is dropped. Schedules are saved as `schedules.json` in `$STATE_DIRECTORY` (written to a temporary file, then renamed) and set again at startup. A schedule can't run any of the three commands, and the bot ignores its own posts, so a schedule can't loop. The text is never logged.

## What the bot needs from signal-cli

Only the socket. The bot speaks JSON-RPC to it and never touches signal-cli's data directory, where the account keys live.

The socket's permissions decide who may connect, and the bot is let in through a Unix group, not a user id, so a transient `DynamicUser` works:

- `signalbot.service` runs with `DynamicUser=yes` and `SupplementaryGroups=signal-cli`, so its throwaway user is in the group.
- Docker's `--group-add` puts the container's user in the same group. The container mounts only the socket's directory, so the data directory isn't there to read.
- signal-cli should create the socket group-writable (`0770`, from `UMask=0007`) in a directory the group can search (`0750`). A default umask gives `0755` and locks out even the group.

Everyone outside the Unix group gets "Permission denied". The group is the only access control: anyone in it can drive the Signal account, so keep it to the bot.

The bot's keys stay out of reach in two ways. It runs as a different user from signal-cli, and the data directory is mode `0700`, so it can't be searched. That mode matters: `UMask=0007` makes files signal-cli creates group-accessible, and the bot is in that group, so with a `0755` directory it could read them (tested). Also, `ProtectHome=yes` hides `/home`, where signal-cli keeps its data by default (`~/.local/share/signal-cli`). Data kept elsewhere, such as `/var/lib/signal-cli`, relies on the directory mode alone; add it to `InaccessiblePaths=` in the unit to hide it outright.

A TCP socket (`--tcp 127.0.0.1:7583`) needs none of this, but then any local user can connect and control or spy on the Signal account (PRIVACY RISK).
